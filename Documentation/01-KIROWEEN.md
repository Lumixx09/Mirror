# Kiroween 2026

## Competition Requirements, Credits and Submission Strategy

**Project:** MIRROR\
**Category selected:** Frankenstein\
**Competition:** https://kiroween.devpost.com/\
**Rules:** https://kiroween.devpost.com/rules

> This document is an operational checklist, not a substitute for the
> live official rules. Recheck the event page and rules before
> submission because organizers may update instructions.

## 1. Competition operating principles

MIRROR must be newly developed within the competition's eligible
development period and must demonstrate meaningful use of Kiro. Do not
misrepresent the extent of Kiro usage or fabricate development history.

The public submission should provide: - Working, publicly accessible
application - Public source repository - Open-source licence - Root
`.kiro` directory - Clear setup and usage instructions - Demonstration
video meeting the current duration limit - Accurate explanation of how
Kiro contributed

Check the official page for exact category wording, eligibility,
deadlines, credit redemption and submission fields.

## 2. Credit allowance

The event advertises up to 4,000 free Kiro credits for eligible
participants. Do not assume credits are available until the request is
approved and the balance is visible in the account.

Owner actions: 1. Register for the competition. 2. Open the Resources
section on Devpost. 3. Find the Kiro credit request form. 4. Enter the
correct Kiro user ID or AWS account ID requested by the form. 5. Submit
the request before its deadline. 6. Monitor approval and redemption
instructions. 7. Redeem credits before the stated expiry. 8. Verify that
the credits appear in the correct account.

Never place account passwords, recovery codes or private credentials in
project files or agent prompts.

The competition information previously reviewed stated a December 1,
2026, 12:00 PM Pacific credit request deadline and a December 4, 2026,
2:00 PM Pacific submission deadline. Reconfirm these on the official
page. December 4 at 2:00 PM Pacific is 10:00 PM UTC and 11:00 PM in
Nigeria (WAT), subject to any official update.

## 3. Credit discipline

Treat credits as a finite resource.

Planning allocation (not a measured Kiro billing estimate): - 10%
specifications and architecture - 55% implementation - 20% testing and
debugging - 10% refinement - 5% contingency

Good practices: - Inspect existing code before editing. - Ask for
targeted changes rather than whole-project regeneration. - Work from
small Kiro spec tasks. - Avoid multiple agents duplicating the same
work. - Reuse tested components. - Run targeted tests after changes. -
Do not repeatedly request broad codebase summaries. - Keep a
`CREDIT_USAGE.md` with observed balance and usage only when the account
exposes it. - Never invent credit consumption figures.

## 4. Kiro must be part of the actual development process

Use Kiro features that materially help build MIRROR: - Specs for
requirements, design and tasks - Steering for persistent project
constraints - Hooks for repeatable quality checks - Custom agents for
distinct engineering responsibilities - MCP integrations only when
useful and approved - Powers or reusable workflows where supported and
genuinely useful

Do not add features merely to make the submission sound more advanced.

## 5. Kiro evidence

Maintain genuine evidence of Kiro use: - Committed `.kiro/specs` -
Committed `.kiro/steering` - Committed hooks and agent configuration
where supported - Relevant development screenshots - Real task and
specification history - Tests generated or improved through the
workflow - Architectural decisions - Bugs discovered and resolved

Do not publish private credentials, personal account data or sensitive
screenshots.

## 6. Category alignment: Frankenstein

The project combines distinct technical capabilities into one coherent
product: - Isolated browser automation - Controlled experimentation -
DOM and semantic comparison - Visual and behavioural analysis - Evidence
integrity - AI-assisted investigation

The category explanation should focus on the meaningful integration and
the resulting capability, not simply list technologies.
